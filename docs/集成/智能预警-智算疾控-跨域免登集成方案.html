01背景与集成目标

1.1 系统现状

系统名称架构域名角色定位
系统 A智能预警B/S独立域名（与 B 非同域）用户登录入口 / 集成发起方
系统 B智算疾控B/S独立域名（与 A 非同域）被嵌入 / 被跳转方（能力提供方）

1.2 集成目标

  1. 用户在 A 内登录后，通过页面跳转或 iframe 嵌入方式访问 B 的功能页面，无需在 B 重复登录（免登）；
  2. 跨域传递 A 侧用户身份与上下文信息（用户 ID、用户名、租户 ID、租户编码、所属区域、备注信息），全程密文传输，禁止明文；
  3. 采用 URL 参数方式传递：clientId（客户端标识）+ verifyData（加密数据）；
  4. 加密能力由 A 后端提供加密接口实现（密钥由 B 分发，A 侧不参与解密）；
  5. B 侧拦截 → 解密 → 校验 → 建立 B 自身会话，形成完整闭环；
  6. 支持数据时效控制（默认 5 分钟）与防重放，提升整体安全强度。

1.3 方案总览（一句话）

💡 集成模式 本方案本质是一套轻量级加密票据式免登（Encrypted Ticket SSO）：A 后端作为"票据签发方"用 B 的密钥加密用户信息生成一次性票据 verifyData，B 作为"票据验证方"解密验票后建立自己的会话。A 与 B 之间无运行时接口耦合（B 不需要回调 A），仅通过密文票据完成身份信任传递。

02角色职责与术语定义

2.1 双方职责矩阵

事项系统 A（智能预警）系统 B（智算疾控）
clientId 注册与密钥分发向 B 申请接入，提供接入方信息，安全保管密钥为 A 分配 clientId 与加密密钥，密钥仅通过安全渠道线下交付
加密接口提供：内部加密接口（需登录态鉴权），用 B 密钥加密当前用户信息不涉及（B 不参与 A 的加密过程）
跳转发起提供：前端获取票据 → 拼接 URL 跳转 / iframe 加载 B 页面不涉及
拦截与解密不涉及提供：前端拦截 URL 参数，后端解密验证 + 时效/防重放校验
B 会话管理不涉及提供：会话创建、续期、登出；iframe 场景的 Cookie 跨域策略
密钥轮换配合更换密钥，新旧密钥过渡期内兼容主导：定期生成新密钥并安全交付，维护密钥版本

2.2 术语表

术语定义
clientIdB 侧为每个接入方（当前仅 A）分配的客户端唯一标识，用于 B 定位对应的解密密钥
verifyData密文票据：包含 B 可识别的密钥版本、随机 IV、AES-GCM 密文与认证标签，整体 Base64URL 编码后的字符串
明文载荷（payload）verifyData 解密后的 JSON：用户信息 + 时间戳 + expireAt + nonce
一次性票据verifyData 被成功验证后立即作废（nonce 落库/缓存），同一 verifyData 不可二次使用
时效窗口票据自签发到被验证的最大允许时间差，默认 5 分钟（300 秒）

3.1 端到端时序图

3.2 关键设计决策说明

决策点结论与理由
为何由 A 后端加密而非前端密钥绝不能下发到浏览器（前端 JS 可被完整提取）。加密接口放在 A 后端，密钥仅存在于服务端内存/密钥存储中
为何采用票据而非直接调 B 登录接口URL 票据天然适配"跳转 + iframe 嵌入"两种形态（iframe 无法携带跨域自定义 Header），且 A、B 零运行时耦合，B 不需要感知 A 的登录体系
为何选 AES-GCMAEAD 认证加密：一次加密同时获得机密性 + 完整性 + 防篡改，密文被改动 1 个 bit 都会解密失败，无需额外 HMAC。如需国密合规可平替为 SM4-GCM（结构不变）
为何 verifyData 要一次性URL 参数可能进入浏览器历史、代理与访问日志，一次性票据可将泄露后的重放风险窗口压缩到接近零

04密钥与客户端（clientId）管理规范

4.1 clientId 登记信息（B 侧维护）

B 侧需建立接入方密钥登记表（建议表结构，字段注释齐全）：

-- B 系统：跨域免登客户端密钥登记表（示例 DDL，MySQL）
CREATE TABLE t_sso_client (
  id            BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
  client_id     VARCHAR(64)  NOT NULL COMMENT '客户端ID，如 CDSS-A-ALERT-001',
  client_name   VARCHAR(128) NOT NULL COMMENT '客户端名称，如：智能预警',
  key_version   INT          NOT NULL DEFAULT 1 COMMENT '密钥版本号，用于轮换',
  secret_key    VARCHAR(256) NOT NULL COMMENT 'AES-256 密钥(Base64)，生产建议加密存储/KMS托管',
  status        CHAR(1)      NOT NULL DEFAULT '0' COMMENT '状态（0启用 1停用）',
  expire_window INT          NOT NULL DEFAULT 300 COMMENT '允许的票据时效窗口(秒)，默认300',
  remark        VARCHAR(512) DEFAULT NULL COMMENT '备注',
  create_by     VARCHAR(64)  COMMENT '创建人',
  create_time   DATETIME     COMMENT '创建时间',
  update_by     VARCHAR(64)  COMMENT '更新人',
  update_time   DATETIME     COMMENT '更新时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_client_id (client_id),
  KEY idx_status (status)
) COMMENT='跨域免登客户端密钥登记表';

4.2 密钥分发与轮换约定

环节规范
生成由 B 侧使用安全随机数生成（SecureRandom，32 字节 = 256 位），生成过程留审计记录
分发⚠️ 禁止 IM / 邮件明文传输 通过密码管家 / 加密压缩包 + 口令分渠道传递（压缩包走 IM、口令走电话），或当面交付
存储双方均不得写入代码仓库、配置文件明文；建议环境变量注入或配置中心加密项（Nacos 加密配置）
轮换建议每 3 个月轮换一次；轮换采用 keyVersion 递增，新旧版本并行 48 小时过渡期后旧版本停用
泄露应急B 侧立即将对应 clientId 置为停用状态，通知 A 并启用新密钥；对泄露窗口期内已验证成功的会话评估是否强制下线
⚠️ 密钥版本嵌入密文首字节 verifyData 二进制结构首部含 1 字节 keyVersion（见第 5 章），B 解密时按「clientId + keyVersion」定位密钥，实现无缝轮换，无需增加额外 URL 参数。

05数据加密规范（verifyData）

5.1 算法与参数

项目规范值说明
加密算法AES-256-GCMAEAD 认证加密；如项目要求国密，可等价替换为 SM4-GCM（数据结构与流程完全一致）
密钥长度256 bit（32 字节）由 B 生成并分发
IV（Nonce）12 字节安全随机每次加密必须重新随机生成，严禁固定 IV / 复用 IV（GCM 复用 IV 是致命漏洞）
认证标签 Tag128 bit（16 字节）由 GCM 自动生成并校验，防篡改
编码方式Base64URL（无 padding，-/_ 字符集）URL 安全，避免二次转义

5.2 明文载荷（payload）字段定义

字段类型必填说明
userIdString✅A 侧用户唯一 ID
userNameString✅用户名/姓名
nickNameString✅用户昵称（B 侧界面展示用）
tenantIdString✅租户 ID
tenantCodeString✅租户编码
tenantNameString✅租户名称（B 侧界面展示用）
regionCodeString✅所属区域编码（行政区划代码）
regionNameString➖所属区域名称
timestamplong✅签发时间戳（毫秒，UTC）
expireAtlong✅过期时间戳（毫秒）= timestamp + 300_000
nonceString✅一次性随机串（UUID v4，128 bit 以上随机性），防重放
remarkString➖其他备注信息（自定义扩展，注意不要放敏感凭据）
📌 明文 JSON 示例 
{ "userId":"U10001", "userName":"张三", "nickName":"预警小张",
  "tenantId":"T001", "tenantCode":"HUBEI_CDC", "tenantName":"湖北省疾控中心",
  "regionCode":"420000", "regionName":"湖北省",
  "timestamp":1756641000000, "expireAt":1756641300000,
  "nonce":"9f8b7c6d-1e2f-4a3b-8c7d-5e6f7a8b9c0d", "remark":"from-alert" }

5.3 verifyData 二进制结构与最终形态

┌──────────────┬────────────┬─────────────────────┬──────────────┐
│ keyVersion   │ IV (12B)   │  AES-GCM 密文        │ Tag (16B)    │
│ 1 字节       │ 随机       │  (明文 payload JSON) │ 认证标签      │
└──────────────┴────────────┴─────────────────────┴──────────────┘
                         │
                         ▼  整体 Base64URL 编码（无 padding）
verifyData = base64url( keyVersion(1B) ‖ IV(12B) ‖ ciphertext ‖ tag(16B) )
  • AAD（附加认证数据）：建议将 clientId 字符串作为 GCM 的 AAD 参与认证 —— 票据被挪用到其他 clientId 时解密直接失败，进一步收紧绑定关系（可选项，双方约定一致即可）。
  • 长度预估：明文约 300 字节 → 密文二进制约 330 字节 → Base64URL 后约 440 字符，URL 总长可控（浏览器上限 2KB+），无超长风险。

06接口详细设计

6.1 【A 后端】获取免登票据接口（A 内部接口）

路径POST /api/sso/ticket
鉴权必须携带 A 登录态（Cookie 或 Token），未登录返回 401 —— 防止匿名用户批量刷票据
限流按用户限流（如 10 次/分钟），按 IP 限流兜底，防刷
请求体可空；或 { "target":"B", "remark":"..." }（扩展用）
// 响应示例
{
  "code": 0,
  "msg": "ok",
  "data": {
    "clientId": "CDSS-B-ZJJK-001",        // B 分配给 A 的客户端 ID
    "verifyData": "AQAAeU9x...",           // Base64URL 密文票据
    "expireAt": 1756641300000              // 票据过期时间（供前端提示用）
  }
}

处理逻辑（A 后端）

  1. 校验 A 登录态，取当前用户信息（userId、userName、nickName、tenantId、tenantCode、tenantName、regionCode 等）；
  2. 生成 nonce（UUID v4）与 timestamp / expireAt（当前时间 +300 秒）；
  3. 组装 payload JSON → 取 B 密钥（当前 keyVersion）→ AES-256-GCM 加密（IV 随机生成，clientId 作 AAD）；
  4. 拼装 keyVersion + IV + 密文 + Tag → Base64URL → 返回。

6.2 【A 前端】跳转规则

// 跳转场景
window.location.href = `https://B域名/targetPage?clientId=${clientId}&verifyData=${verifyData}`;
// iframe 嵌入场景
iframe.src = `https://B域名/targetPage?clientId=${clientId}&verifyData=${verifyData}`;
  • verifyData 为 Base64URL 编码，无需再 encodeURIComponent（若实现方使用了标准 Base64，则必须 encodeURIComponent，双方在联调时对齐）；
  • 票据即取即用：前端不要缓存票据复用（一次性消费，第二次会失败）。

6.3 【B 后端】票据验证与会话初始化接口

路径POST /sso/auth/verify（Content-Type: application/json）
鉴权免鉴权（匿名入口），但必须做限流 + nonce 防重放 + 失败锁定
请求体{ "clientId": "xxx", "verifyData": "yyy", "redirect": "/targetPage" }

处理逻辑（B 后端，按序校验，任一失败即终止）

  1. clientId 合法性：查 t_sso_client，不存在或已停用 → 拒绝（错误码见 6.4）；
  2. Base64URL 解码 → 解析 keyVersion / IV / 密文 / Tag（长度不合法 → 拒绝）；
  3. keyVersion 有效性：取对应版本密钥（过渡期内新旧并行）；
  4. AES-GCM 解密（clientId 作 AAD）：Tag 校验失败 = 数据被篡改或密钥不匹配 → 拒绝；
  5. 时效校验：now ≤ expireAt 且 timestamp ≤ now（防未来时间票据）；超出时效窗口 → 返回"票据已过期"；
  6. 防重放校验：检查 nonce 是否已消费（Redis SETNX sso:nonce:{nonce}，TTL = 时效窗口 + 5 分钟）；已存在 → 拒绝；不存在 → 占用；
  7. 身份映射：按 A 传来的 tenantId/userId 映射或自动开通 B 侧账号（首次进入自动建户策略由 B 决定，见 6.5）；
  8. 建立 B 会话：签发 B 自身会话（见 6.5 Cookie 策略），记录审计日志。
// 成功响应
{
  "code": 0,
  "msg": "ok",
  "data": {
    "user": { "userId":"U10001", "userName":"张三", "nickName":"预警小张", "tenantId":"T001",
              "tenantCode":"HUBEI_CDC", "tenantName":"湖北省疾控中心", "regionCode":"420000" },
    "sessionEstablished": true
  }
}
// 失败响应（错误码见 6.4）
{ "code": 40002, "msg": "票据已过期，请从智能预警系统重新进入" }

6.4 统一错误码约定

错误码场景用户提示（前端展示）安全处置
40001clientId 不存在 / 已停用接入未授权，请联系管理员记录审计日志（IP、UA）
40002票据过期（超过 5 分钟）链接已过期，请从智能预警系统重新进入普通日志
40003解密失败（篡改 / 密钥不匹配）凭证无效，请从智能预警系统重新进入安全告警日志（疑似攻击）
40004nonce 重复（重放）链接已失效，请重新进入安全告警日志（疑似重放攻击）
40005格式非法（Base64 / 长度不匹配）参数错误限流 + 审计
40006限流触发操作过于频繁，请稍后再试限流日志

6.5 B 会话策略（重点：iframe 跨域场景）

策略项约定
会话载体优先 HttpOnly + Secure + SameSite=None 的 Cookie（iframe 跨域场景下 Cookie 必须为 SameSite=None 才能随 iframe 请求携带）；若 B 前后端分离使用 Token，则 Token 存内存（不落 localStorage）
会话时长与 B 自身登录会话一致（如 30 分钟滑动过期）；iframe 嵌入下建议会话快到期时静默续期，避免 iframe 内弹登录页
首次进入用户方案一（推荐）：B 按 tenantId+userId 自动映射/开通 B 侧影子账号；方案二：校验 B 侧已存在账号，不存在则拒绝并提示先在 B 开通。上线前双方确认采用哪种
登出联动（可选）A 登出时通过 postMessage 通知 iframe 内 B 页面调用登出，或 B 会话独立管理；首期建议B 会话独立管理，二期再联动

07B 系统前端拦截与会话初始化

7.1 拦截逻辑（B 前端路由守卫 / 入口前置逻辑）

// B 前端全局路由守卫（Vue Router 示例，其他框架同理）
router.beforeEach(async (to, from, next) => {
  const { clientId, verifyData } = to.query;
  if (clientId && verifyData) {
    try {
      // ① 上送 B 后端验证，后端 Set-Cookie 建立 B 会话
      await axios.post('/sso/auth/verify', { clientId, verifyData }, { withCredentials: true });
      // ② 立即清洗 URL：移除 clientId / verifyData（防留在浏览器历史与日志）
      const cleaned = { ...to.query }; delete cleaned.clientId; delete cleaned.verifyData;
      next({ path: to.path, query: cleaned, replace: true });
    } catch (e) {
      // ③ 展示 B 侧统一错误页（错误码 → 文案见 6.4）
      next({ path: '/sso-error', query: { code: e.code } });
    }
  } else {
    const hasSession = await checkBSession(); // 探活 B 会话
    hasSession ? next() : next('/sso-error');  // 无票据且无会话 → 引导回 A
  }
});

7.2 关键前端注意事项

  • URL 清洗必须在会话建立后立即执行（replace 而非 push，避免票据进入历史栈）；
  • iframe 嵌入场景，B 的资源加载需全部相对路径或同域 CDN，不能出现第三方阻塞资源；
  • B 侧 X-Frame-Options / CSP frame-ancestors 必须放行 A 的域名（且仅放行 A），防止被其他站点恶意嵌套（点击劫持）；
  • 票据验证失败时，B 错误页提供"返回智能预警"链接（由 B 配置 A 的入口地址）；
  • B 前端应对 /sso/auth/verify 做按钮级防抖，避免用户刷新触发重复验证（nonce 已消费会报 40004，属预期行为，文案已覆盖）。

08时效控制与防重放设计

8.1 时效校验规则（双端时钟）

校验项规则目的
正向时效now > expireAt → 拒绝（40002）票据签发后 5 分钟内必须完成验证
反向时效timestamp > now + 60s → 拒绝（40002）防止伪造"未来时间"票据长期有效
时钟偏差容忍双向各容忍 60 秒（A、B 服务器均需 NTP 校时）消除分布式时钟漂移误杀
⚠️ 上线前置条件 A、B 两台服务器必须开启 NTP 时间同步，且运维在上线检查单中确认。时钟偏差超过容忍窗口会导致大量 40002 误报。

8.2 防重放（nonce 一次性消费）

  • 存储介质：Redis，Key：sso:nonce:{nonce}，Value：clientId；写入方式 SET NX EX（原子占位）；
  • TTL = 时效窗口 + 5 分钟（400 秒）—— 过期后自然清理，无需后台任务；
  • 降级方案：无 Redis 环境可落 MySQL 唯一索引表（uk_nonce），但高并发下推荐 Redis；
  • 验证顺序：nonce 占位放在解密成功之后（避免攻击者用伪造 nonce 恶意占用存储）。

8.3 安全增益总结

时效（5 分钟）+ nonce 一次性 + URL 清洗三重叠加后，即使 verifyData 泄露到浏览器历史 / 代理日志，攻击者拿到时票据已失效或已被消费，实际可利用窗口趋近于零。

10.1 开发阶段强制约定

A

10.2 已识别的典型坑（实现前必读）

  1. SameSite 陷阱：Chrome 80+ 默认 SameSite=Lax，iframe 跨域下 B 的 Cookie 不携带 → B 必须显式设置 SameSite=None; Secure，且 B 必须全站 HTTPS；
  2. Base64 变体混淆：标准 Base64 的 +/= 在 URL 中会被转义或截断，双方必须统一 Base64URL（-_ 无 padding）；
  3. 时钟漂移误杀：上线前用 date 命令核对两台服务器时间，偏差 > 30 秒先修 NTP 再联调；
  4. iframe 中弹窗/新开标签：B 页面内 target="_blank" 新开的页面不继承票据，需保证 B 会话 Cookie 已建立即可正常访问；
  5. 网关/Nginx 参数截断：个别网关对 URL 长度有限制（默认 4K 足够，但若有 WAF 自定义规则需确认不拦截长 query 参数）；
  6. 重复验证：用户在票据验证进行中刷新页面 → nonce 已被消费 → 40004。前端文案已覆盖（"请重新进入"），同时 B 可在会话已建立的情况下直接放行而非报错（先探活会话再报错的顺序，见 7.1 代码）。

A.1 加密工具（A、B 双方共用同一套编码约定）

import javax.crypto.Cipher;
import javax.crypto.spec.GCMParameterSpec;
import javax.crypto.spec.SecretKeySpec;
import java.nio.ByteBuffer;
import java.security.SecureRandom;
import java.util.Base64;

public class SsoCipherUtil {

    private static final int IV_LEN = 12;      // GCM 推荐 IV 长度（字节）
    private static final int TAG_BITS = 128;  // 认证标签长度（bit）
    private static final SecureRandom RANDOM = new SecureRandom();

    /** 加密：payload(明文JSON) → verifyData(Base64URL)。aad 建议传 clientId */
    public static String encrypt(byte[] keyBytes, int keyVersion, String payload, byte[] aad) {
        try {
            byte[] iv = new byte[IV_LEN];
            RANDOM.nextBytes(iv);                                  // 每次随机 IV，严禁复用

            Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
            cipher.init(Cipher.ENCRYPT_MODE, new SecretKeySpec(keyBytes, "AES"),
                        new GCMParameterSpec(TAG_BITS, iv));
            if (aad != null) cipher.updateAAD(aad);          // clientId 作 AAD 绑定
            byte[] cipherText = cipher.doFinal(payload.getBytes("UTF-8"));

            // 结构：keyVersion(1B) + IV(12B) + ciphertext(含tag)
            ByteBuffer buf = ByteBuffer.allocate(1 + IV_LEN + cipherText.length);
            buf.put((byte) keyVersion).put(iv).put(cipherText);
            return Base64.getUrlEncoder().withoutPadding().encodeToString(buf.array());
        } catch (Exception e) {
            throw new IllegalStateException("SSO encrypt failed", e);
        }
    }

    /** 解密：verifyData → payload(明文JSON)。返回 [0]=keyVersion, [1]=明文 */
    public static Object[] decrypt(byte[] keyBytes, String verifyData, byte[] aad) {
        try {
            byte[] all = Base64.getUrlDecoder().decode(verifyData);
            if (all.length < 1 + IV_LEN + 16) throw new IllegalArgumentException("verifyData 长度非法");

            int keyVersion = all[0] & 0xFF;
            byte[] iv = new byte[IV_LEN];
            System.arraycopy(all, 1, iv, 0, IV_LEN);

            Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
            cipher.init(Cipher.DECRYPT_MODE, new SecretKeySpec(keyBytes, "AES"),
                        new GCMParameterSpec(TAG_BITS, iv));
            if (aad != null) cipher.updateAAD(aad);
            byte[] plain = cipher.doFinal(all, 1 + IV_LEN, all.length - 1 - IV_LEN); // Tag校验失败将抛异常

            return new Object[]{ keyVersion, new String(plain, "UTF-8") };
        } catch (Exception e) {
            throw new IllegalStateException("SSO decrypt failed (疑似篡改或密钥不匹配)", e);
        }
    }
}

    byte[] key = resolveKey(client, req.getClientId());  // 按 keyVersion 解析密钥（新旧并行）

    securityLog.warn("[SSO] 解密失败 clientId={}", req.getClientId());  // 40003

}

    return Result.fail(40002);                                    // 过期 / 未来票据
