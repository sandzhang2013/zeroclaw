## 下次怎么快

在 `feat/multi-user-isolation` 上操作。不要切到 `master` 再把功能分支丢掉。

0. 先把身份融合提交到分支上，再合并。融合锚点在 `trusted_proxy.rs`、`session_backend.rs`、`session_sqlite.rs`、`api.rs`、`ws.rs`、`tenant_scoped.rs`、`agent_scoped.rs`、`retrieval.rs`、`memory/sqlite.rs`。这些必须在 `HEAD` 里，三方合并才认得。提示页、部署脚本、页面布局可以另一次提交，或留在 stash；不要和融合锚点打在同一个 stash 里。

1. 收起还没提交的产品改动，包含未跟踪文件。融合已经在分支上时，不要再 stash 那九个文件。

   ```bash
   git status --short
   git stash push -u -m "wip before merging master"
   git fetch origin master:master
   git merge master --no-edit
   ```

2. 冲突按下面的表处理。一边为空就留另一边。不要 `git checkout --ours` 整文件。

3. 锁文件只解决冲突标记，然后让 cargo 自己重写。不要手改大段 `Cargo.lock`。

   ```bash
   cargo check -p zeroclaw -p hbcdcagent-bff
   ```

   新依赖不要加 `--offline`。

4. 提交合并。信息用 `merge(master): ...`。然后 `git stash pop`。pop 冲突只解决提示页、部署和前端那些产品改动，不要把 stash 覆盖回第 2 步的取舍。

5. 先跑这条窄测试，再编译两个二进制。全量 `cargo test` 不是每次合入的门槛。

   ```bash
   cargo test -p hbcdcagent-bff
   cargo test -p zeroclaw-gateway --lib trusted_proxy
   cargo test -p zeroclaw-gateway --lib catalog_
   cargo test -p zeroclaw-infra --lib session
   cd web && npm test
   cargo build -p zeroclaw --bin zeroclaw -p hbcdcagent-bff
   ```

6. 要更新页面静态资源时，先按当前 daemon 重新生成前端类型，再构建。

   ```bash
   cargo web gen-api
   cargo web check
   cargo web build
   ```

   `cargo web check` 会再生成一次并跑 `tsc -b`。生成文件通过后再看剩下的类型错误，那些才是真冲突。

7. 重启沿用正在跑的进程环境，不要跑 `deploy/hbcdcagent/scripts/start-local.sh`。那个脚本会读交付包，并把 `deploy/hbcdcagent/.env` 里的占位 secret 盖到 daemon 上。本机 daemon 的 secret 在 `~/.zeroclaw/config.toml`，BFF 必须用同一串。

   daemon 只需要这三个环境变量，secret 继续读配置文件：

   ```bash
   ZEROCLAW_gateway__path_prefix=/hbcdcagent
   ZEROCLAW_gateway__web_dist_dir=<仓库>/web/dist
   ZEROCLAW_gateway__require_pairing=false
   ./target/debug/zeroclaw daemon --host 127.0.0.1 --port 42617
   ```

   BFF 保持 `HBCDCAGENT_BFF_LOCAL_MOCK=true`、`HBCDCAGENT_BFF_LISTEN=0.0.0.0:50002`、`HBCDCAGENT_BFF_PUBLIC_ORIGIN=http://127.0.0.1:50002`，并带上原来的 `USER_CENTER_*` 和与配置文件相同的 `ZEROCLAW_gateway__trusted_proxy_secret`。

8. 合完用这三条确认，不要只看进程在不在。

   ```bash
   curl -sf http://127.0.0.1:42617/hbcdcagent/health
   curl -sf http://127.0.0.1:50002/hbcdcagent/health
   # mock 登录拿到 cookie 后
   curl -sf -H "Cookie: zeroclaw_mock_user=<cookie>" http://127.0.0.1:50002/hbcdcagent/api/status
   ```

   `/api/status` 的 `version` 应是 `0.8.5` 或更新，`agents` 里要有 `hbcdc` 和 `deepseek`。没有 `agents` 时，工作台会退回不存在的 `default`，页面表现为一直重连。

## 冲突时怎么取

| 文件 | 取舍 |
|---|---|
| `Cargo.toml` | 上游成员列表，加上 `crates/hbcdcagent-bff` |
| `crates/zeroclaw-config` | `workbench` 与 `write_lock` 两个模块都留；校验里工作台 caps、费用、配对码长度、`trusted_proxy_secret` 都留 |
| `session_backend.rs` | 留 `session_belongs_to_platform_user`。已有 `principal_id` 时必须等于 `user:{user_id}`；主体为空才退回 `user_id`。列表过滤用这个函数 |
| `session_sqlite.rs` | 用上游的表结构和迁移。列表过滤改回 `session_belongs_to_platform_user`。上游加列时，SELECT 下标跟结构体对齐，不要手改一半 |
| `session_store.rs` | 本机不用 JSONL。`user_id` 旁路文件留着。上游若给 JSONL 加了 `principal_id`，用上游的。不要在这里接省统筹 |
| `memory/sqlite.rs` | 共享平面查询留「租户条件 AND `principal_id IS NULL`」。私有写入的 `ON CONFLICT` 用 `(agent_id, ifnull(tenant_id, ''), key)`，不要退回上游的 `(agent_id, key)`。`migrate_sqlite_memory_tenant_unique` 之后再调用一次 `init_schema`，否则重建表会丢掉 `principal_id` |
| `tenant_scoped.rs` | 共享平面继续按 `UserAttrs.user_id` 盖 `tenant_id`。`*_for_principal` 交给 `principal_scope`：普通用户只能碰自己的租户，管理员不改写已经钉住的会话主人 |
| `agent_scoped.rs` / `retrieval.rs` | 上游若已转发 `*_for_principal`，用上游的。没有就在 `Memory` 实现末尾补转发。`retrieval` 在私有写入、删除、清理后清缓存 |
| `zeroclaw-gateway/src/lib.rs` | 技能中心路由留在主路由。配置类路由若上游已经挂在 `config_route_auth` 上，不要在主路由再挂一次。合完搜重复 `.route("` |
| `ws.rs` | 用上游的 turn 循环。接回三处：`Ok(true)` 调 `stamp_platform_session_owner`；`user_id` 已是当前用户且 `principal_id` 为空时补写主体；Agent 建好后 `route_memory_to_principal`，主体用会话主人，租户用平台 `user_id`，agent 用当前别名。管理员打开别人的会话不改主人。`scope_user_attrs` 套在上游 scope 外面。类型递归溢出时，crate 根上 `#![recursion_limit = "256"]` |
| `api.rs` | `session_visible_to` / `require_session_access` 用 `session_belongs_to_platform_user`。对上了就补齐缺的 `principal_id` 或 `user_id`。两列都空时，第一个打开的用户认领。管理员在这之前就返回，不改写主人。`PairingGuard::new` 保留配对码策略参数 |
| `api_config.rs` / `api_workbench.rs` | `persist_and_swap(state, authorization, config, guard)`。工作台保存前走 `authorize_config_write`。错误值已经是 `Response`，不要再包一层 `error_response` |
| `trusted_proxy.rs` | `Principal::from_identity(Roster)`，`principal_id` 传平台 `user_id`，得到 `user:{user_id}`。留 `roster_principal_id` 和 `stamp_platform_session_owner`（同时写 `user_id` 和主体）。角色留在 `UserAttrs` |
| `approval` / `shell` / `seatbelt` / `detect` / `file_write` | 用上游的沙箱和 capability。功能分支的技能目录、上传结果 JSON、自主权上限接回去 |
| `web/src/router` | 保留工作台和 `OpsGate`，加上 `/plugins` |
| `web/src/types/api.ts` | `StatusResponse` 用生成类型再交叉 `{ agents?: string[] }`，等 `cargo web gen-api` 把 `agents` 写进 spec 后再去掉交叉 |
| `docs/book` 的 ADR 索引 | 新编号接着上游最大号。不要把功能分支的 ADR-014/016 写回已被上游占用的号 |
| `Cargo.lock` | 依赖名：只有一个版本就用不带版本的名字；同一 crate 两个版本就带版本后缀（这次是 `ghash 0.6.0`） |

## 合并前就守住的边界

热文件每次还会撞。新功能不要再往里面加。登录、页面、技能留在各自的文件里，热文件只保留下面这些锚点：

- 登录、票据、cookie、页面注入只改 `crates/hbcdcagent-bff`。不要把用户中心协议写进 `zeroclaw-gateway`。
- 工作台页面和首页目录只改 `web/src` 里工作台文件，加上 `api_workbench.rs`。
- 技能广场、个人技能只改 `api_skill_center.rs` 和对应前端。新 HTTP 路径先在 `lib.rs` 里搜一遍。
- 用户是谁：BFF 冻结在 `UserAttrs`。会话主人是 `user:{user_id}`。不要给 `Principal` 加 `user_id` 或 `roles`。
- 热文件只允许融合锚点（盖章、归属、私有记忆转发、`ON CONFLICT` 目标、租户迁移后再 `init_schema`）。产品文案、页面、用户中心协议不要写进 `session_sqlite.rs`、`memory/sqlite.rs`、`ws.rs`。
- 前端响应类型以 `cargo web gen-api` 为准。手写一份 `StatusResponse` 会在下一次生成后对不上。
